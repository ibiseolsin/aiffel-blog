초록 체크가 놓친 일곱 장면 — 배포 아홉 날을 다시 읽기

Mini WRAP UP · 아이펠 「AI 서비스 인 프로덕션」 노드 63~71 · 2026년 10월 30일 · 김지훈

아홉 날 동안 배운 장치는 모두 「성공 표시가 놓친 실패」를 하나씩 막으려고 생겼어요. CI, staging, Dockerfile, 한 번 빌드, 블루그린, 스타트업 프로브가 다 그래요.

가장 극적인 장면은 마지막 날이었어요. 배포 명령은 성공했는데 30초 동안 모든 요청이 실패했고, /health 프로브 설정 한 줄로 실패가 0건이 됐어요.

이 글은 그 일곱 장면을 표로 모으고, 각 장면을 잡아낸 장치가 배포 길의 어디에 있는지 눌러 볼 수 있게 정리했어요.

아홉 날을 계단 하나로

이 모듈은 「AI 친구 에이전트」 하나를 끝까지 들고 갔어요. 캐릭터가 대화를 기억하고, 날씨를 찾아 답하고, 약속을 저장해 먼저 말을 거는 서비스예요. 날마다 새 기술이 나왔지만, 실은 전날 남은 문제 하나를 받아서 푸는 계단이었어요.

예를 들어 3일째 마무리에는 「배포할 때마다 사람이 명령을 실행해 잘못된 설정이 그대로 배포될 수 있다」는 한계가 적혀 있어요1. 그 문장이 4일째 GitHub Actions 자동 배포의 출발점이 돼요. 이렇게 한 날의 끝 문장이 다음 날의 첫 문제가 되는 구조라서, 순서를 바꿔 배우면 각 장치가 왜 필요한지 잘 안 보여요.

초록 체크가 놓친 일곱 장면

택배 앱에 「배송 완료」가 떴는데 문 앞에 상자가 없는 경우가 있어요. 문자는 택배 기사가 정한 완료 조건을 통과했다는 뜻이지, 내가 물건을 받았다는 뜻은 아니에요. 배포의 초록 체크도 똑같았어요.

재미있는 건 4일째 사고 두 개의 대비예요. 환경변수 이름을 바꿔 앱이 시작조차 못 한 사고는 Actions가 빨갛게 실패했지만, Cloud Run이 이전 리비전에 트래픽 100%를 남겨 둬서 사용자는 아무 영향이 없었어요. 정말 위험했던 건 초록으로 끝난 쪽이었어요.

성공 표시와 실제가 어긋난 장면은 날마다 하나씩 있었어요
날초록으로 보인 것실제로 일어난 일막은 장치
3일답이 화면에 나옴타임아웃에 「내일 서울은 맑다가」에서 잘려 비 소식이 사라짐타임아웃 설정, 스트림 종료 확인

8일째 교재 문장이 이 표를 한 줄로 요약해요. 요청은 끊기지 않고 옮겨 갔지만 「사용자 입장에서는 친구가 방금 나눈 대화를 잊어버린 것이라 무중단 배포라고 하기 어렵다」2. 요청이 안 끊기는 것과 하던 일이 이어지는 것은 다른 문제였어요.

장치를 배포 길 위에 놓으면

9일째가 끝나면 PR 하나가 production에 닿기까지 아래 일곱 칸을 지나요. 위 표의 장면을 고르면 그 실패를 잡는 칸이 표시돼요.

  1. PR을 올리면 CI가 테스트를 돌리고, 통과해야 머지돼요(5일). 잡는 장면: 4일 17:00 약속 — 러너가 UTC라 서버와 같은 조건에서 실패해요.
  2. Dockerfile로 이미지를 만들어요. 베이스 이미지, 시스템 패키지, 실행 사용자까지 파일에 적혀 있어요(6일). 잡는 장면: 6일 OCR 500 — tesseract 설치 줄이 이미지에 들어가요.
  3. 이미지는 Actions에서 한 번만 만들고 커밋 SHA로 태그를 붙여요(7일). 잡는 장면: 7일 다른 이미지 — 어느 커밋인지 바로 찾을 수 있어요.
  4. staging에 배포하고 사람이 화면을 직접 열어 봐요(5일). 잡는 장면: 5일 사라진 버튼 — 테스트는 화면 모양을 보지 않아요.
  5. 승인을 받으면 staging에서 확인한 다이제스트 그대로 production에 트래픽 0%로 올려요(7·9일). 잡는 장면: 7일 다른 이미지 — 다시 빌드하지 않고 승격해요.
  6. /health 프로브와 스모크 테스트를 통과하면 100%로 옮기고, 이상하면 버튼 하나로 이전 리비전에 되돌려요(9일). 잡는 장면: 9일 30초 503 — 준비가 끝난 뒤에만 트래픽이 가요.
  7. 운영 중에는 상태를 DB에 두고, 타임아웃·LLM 월 한도·로그로 지켜봐요(3·8일). 잡는 장면: 3일 잘린 답, 8일 잊힌 대화.

칸마다 사람이 하는 일이 하나씩 남아 있어요. staging 화면 보기, production 승인 누르기, 롤백 판단하기예요. 교재는 승인을 에이전트에게 맡기지 말고 직접 누르라고 해요.

한 장면 크게 보기: 30초

9일째 실험은 시작이 느린 AI 서비스를 흉내 냈어요. 앱이 포트는 바로 열지만 모델 설정이나 문서 색인을 불러오느라 30초 동안 모든 요청에 503을 돌려주게 만든 거예요.

기본 프로브는 포트가 열렸는지만 봐요. 그래서 Cloud Run은 준비됐다고 판단해 트래픽을 옮겼고, 그 뒤 30초 동안 보낸 메시지는 모두 실패했어요. 그런데 배포 명령은 성공으로 끝났어요. 교재 문장이 이 글의 제목이 됐어요. 「배포가 성공했다는 것은 Cloud Run이 정한 준비 조건을 통과했다는 뜻일 뿐이고, 사용자가 오류를 보지 않았다는 뜻은 아닙니다.」

30초 → 0건--startup-probe=httpGet.path=/health,periodSeconds=5,failureThreshold=12 한 줄의 차이예요

대가도 있어요. 배포가 30초쯤 더 걸리고, 5초 간격 12번(최대 60초) 안에 준비되지 않으면 새 리비전은 실패로 끝나요. 그래도 그때는 트래픽이 옮겨 가지 않으니 사용자는 이전 버전을 계속 써요. 실패가 사용자 쪽이 아니라 배포 쪽에 남는 거예요.

정리하며 헷갈렸던 것

태그와 다이제스트는 뭐가 다른가요?

태그(:latest, 커밋 SHA)는 이름표라 다른 이미지에 옮겨 붙일 수 있어요. 다이제스트(sha256:…)는 이미지 내용으로 정해지는 값이라 바뀌지 않아요. 그래서 「staging에서 본 것과 같은 이미지인가」는 다이제스트로 확인해요. 앞 12자리만 맞춰 봐도 충분하다고 해요.

롤백하면 이미지를 다시 만드나요?

아니에요. Cloud Run 롤백은 트래픽을 이전 리비전으로 되돌리는 것뿐이라 몇 초 안에 끝나요. 대신 스타트업 프로브를 다시 돌리지 않고 DB 같은 바깥 의존성도 확인하지 않아요. 새 버전이 테이블 구조를 바꿨다면 이전 리비전이 그 테이블을 못 읽어서 롤백이 깨질 수 있어요.

고쳐서 배포했는데 왜 옛 버전이 나오죠?

트래픽 고정 때문이에요. 카나리나 롤백으로 트래픽을 특정 리비전에 묶어 두면, 그 뒤 배포는 새 리비전만 만들고 트래픽을 0%에 둬요. 워크플로는 초록인데 사용자는 새 버전을 못 받아요. 일곱 장면과 같은 종류의 함정이고, --to-latest로 풀어요.

--set-env-vars와 --update-env-vars는 왜 구분하나요?

--set-env-vars는 적은 것 말고 나머지 환경변수를 지워요. OCR 스위치 하나 켜려다 ENV=production까지 날리면 개발용 패널이 사용자에게 보여요. 교재가 6·7·9일에 거듭 경고한 플래그예요.

아직 남은 것

교재도 9일째 끝에서 남은 문제를 솔직하게 적어 둬요. 다음에 공부할 목록으로 옮겨 둬요.

  1. 권한이 환경별로 나뉘지 않았어요. staging과 production이 같은 런타임 서비스 계정을 써서 staging도 production의 secret key를 읽을 수 있어요. 데이터는 나눴는데 권한은 못 나눴어요.
  2. 스모크 테스트는 /health와 /version만 봐요. 캐릭터 답이 이상해졌는지는 몰라요. 실제 LLM 답 품질은 테스트로 잡기 어렵다는 5일째 한계가 그대로예요.
  3. 테이블 구조를 바꾸는 배포는 시험하지 않았어요. 8일째 나온 확장-축소 패턴(새 열 추가 → 두 열을 함께 쓰는 버전 → 옛 열 삭제)을 실제로 해 봐야 해요.

9일째 마무리 문장이 이 모듈을 가장 잘 요약해요. 아침에는 초록 체크만 봤다면, 이제는 준비 조건, 트래픽 설정, 측정할 요청이라는 이름으로 부족한 점을 짚을 수 있어요. 「배송 완료」 문자를 받으면 이제 문 앞부터 확인하게 될 것 같아요.
